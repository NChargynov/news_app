# Локальные правила работы с проектом

Правила действуют для всего проекта и для всех агентов, которые работают с его файлами, инструментами и документацией.

## Язык и коммуникация

- Общаться с пользователем и вести документацию на русском языке.
- Сохранять английские имена классов, методов и переменных согласно стилю Dart.
- Кратко описывать выполненные изменения, результаты проверок и оставшиеся ограничения.
- Не утверждать, что приложение работает или проверки пройдены, если это не проверено.

## Защищённые данные: apiKey

- Запрещено читать, просматривать, извлекать, копировать, выводить или изменять значения `apiKey`, включая имена с таким фрагментом независимо от регистра и места хранения.
- Не заменять, не удалять, не переносить и не форматировать объявления и настройки, содержащие `apiKey`.
- Не искать значения ключей в исходниках, истории Git, diff, логах, настройках, переменных окружения или с помощью сетевых запросов.
- Не открывать и не выводить целиком файлы, заведомо содержащие `apiKey`. Допускается работа только с заранее известными участками, которые не содержат защищённых данных и не затрагивают их.
- Не запускать команды, приложение или инструменты, если они могут вывести `apiKey`, в том числе в URL запроса, сообщении об ошибке или HTTP-логах.
- Не включать значения ключей в ответы, документацию, тесты, коммиты и другие артефакты.
- При случайном появлении ключа не повторять и не сохранять его; прекратить действие, которое привело к раскрытию, и сообщить об этом без значения ключа.
- Если задача требует доступа к `apiKey` или его изменения, остановить эту часть работы и объяснить пользователю ограничение. Не обходить запрет другим инструментом.

## Защищённый каталог android/key

- Запрещено читать каталог `android/key` и всё его содержимое, включая вложенные каталоги и файлы.
- Не перечислять его содержимое, не выполнять поиск, не открывать, не копировать и не изменять находящиеся в нём файлы.
- Не получать эти данные через символические ссылки, историю Git, архивы, резервные копии или другие обходные пути.
- До запуска поиска, индексации, анализа, просмотра diff или упаковки проекта исключать `android/key/**` из области обработки.
- Не запускать сборку или иной инструмент, если он требует чтения этого каталога. Сообщить, какая проверка недоступна по этой причине.

## Работа с кодом

- Перед изменениями изучать относящиеся к задаче файлы с соблюдением запретов на доступ к защищённым данным.
- Вносить минимальные изменения, необходимые для выполнения задачи; не проводить несогласованный рефакторинг.
- Сохранять существующую структуру `core` и `features`, разделение на `data`, `domain` и `ui`.
- Использовать принятые в проекте BLoC для состояния, Dio для HTTP и GetIt/Injectable для зависимостей.
- Не переносить сетевую логику в виджеты и не добавлять зависимости от UI в доменный слой.
- Соблюдать null safety и существующий стиль кода; применять `const`, где это уместно.
- Не редактировать генерируемые файлы вручную. При необходимости обновлять их через генератор, только если он не читает защищённые данные.
- Не добавлять и не обновлять зависимости без необходимости для текущей задачи.
- Не добавлять секреты и чувствительные данные в исходники или логи.

## Проверки

- Проверять изменения подходящим способом: анализатором, форматированием разрешённых файлов и существующими тестами.
- Перед запуском проверок убедиться, что их область чтения и изменения не затрагивает защищённые данные. Не запускать форматирование всего проекта без такой проверки.
- Добавлять тесты для новой логики и исправлений поведения, когда они помогают предотвратить повторение ошибки.
- Для изменений только в документации проверять корректность текста, ссылок и оформления.
- Если проверку нельзя выполнить без нарушения локальных правил, не выполнять её и явно указать причину.

## Git и документация

- Сохранять пользовательские изменения; не удалять и не перезаписывать чужую работу.
- Не выполнять разрушительные Git-команды, принудительную отправку или переписывание истории без явного разрешения пользователя.
- Не создавать коммиты и не отправлять изменения в удалённый репозиторий без запроса пользователя.
- Просматривать только относящиеся к задаче и разрешённые изменения; не выводить общий diff, если он может содержать защищённые данные.
- Обновлять README при изменении способов запуска, архитектуры или доступных возможностей.
- Описывать фактическое поведение проекта и отделять реализованные возможности от планов.
